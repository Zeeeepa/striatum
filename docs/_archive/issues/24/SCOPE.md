# GH #24 - SCOPE

Bound scope for GH #24, "supervise send: packet_id from claim-next not
accepted; release --requeue lands repo_write jobs in 'blocked'."

The implementation must make `packet_id` operator-discoverable from
`claim-next` JSON output, make `supervise send` reject obvious wrong-kind
IDs (`msg_*` / `lease_*` / `job_*`) with a useful pointer at the right
field, and make `release --requeue` either honor the requeue for
repo_write jobs or refuse loudly instead of silently parking them in
`blocked`. The skill bundles (`striatum-supervise`,
`striatum-claim-loop`) must carry a worked example that uses only the
JSON paths produced by real CLI output.

This is a narrow operator-discoverability + state-machine fix, not a
broader supervision, packet, or queue redesign.

## 1. Issues covered

- GH #24 - both bugs (Bug 1 packet_id discoverability, Bug 2
  release --requeue silently parking repo_write jobs).
- Skill-bundle worked example for the supervised claim->send loop on
  the `claude_code` profile. The bundle is generated from
  `src/striatum/plugins/templates/claude_code/skills/*.tmpl`; the
  installed `.claude/skills/*` / `.striatum/plugins/.../skills/*`
  copies and the parallel `gemini` / `codex` template directories
  are regenerated by `striatum skills install` and need not be
  hand-edited.

## 2. Chosen approach

### 2.1 Bug 1 - packet_id discoverability

Use the **smallest-change** path from SPEC option (1), augmented with
the most-useful hint from SPEC option (2):

- Surface `data.packet_id` at the top level of the `claim_next`
  response alongside `data.status` and `data.packet`. The packet's
  internal `packet_id` already exists at `data.packet.packet_id`
  (`go/pkg/mutations/claim.go:217` in the Go builder; mirrored by the
  PG handler that returns `{"status": "claimed", "packet": packet}`
  in `src/striatum/daemon_pg/handlers/workflow_loop/claim_next.py:153`).
  The fix lifts `packet_id` so a `jq -r .data.packet_id` is reliable
  without spelunking.
- Additionally, emit `data.next_steps.supervise_send` containing the
  literal command line `striatum supervise send --session-id <S>
  --packet-id <P>` so the obvious copy-paste shape lives in the
  first few KB of output, mirroring the existing
  `data.packet.commands` block.

Justification: option (3) "implicit lookup by session" would require
changing the `supervise send` RPC contract and the
`HandleSuperviseSend` signature in
`go/pkg/mutations/supervision_control.go:218`; that is a larger,
contract-breaking change. The current claim path already knows
`packet_id`, so surfacing it costs one line in the handler response.
The `next_steps.supervise_send` field is generated, not parsed by
the daemon; it gives operators a guaranteed-correct command without
extending any RPC method. Both changes are additive (no existing
consumer is broken).

### 2.2 Bug 1b - useful `supervise send` error

Today `loadWorkPacket` in
`go/pkg/mutations/supervision_control.go:600-617` raises
`not_found: could not find work packet for packet_id=%q` regardless
of the value. The fix detects the obvious wrong-kind prefixes
(`msg_`, `lease_`, `job_`, `sess_`, `sup_`) before the database
lookup and returns a `not_found` whose message names the wrong-kind
and points at `data.packet.packet_id` / the new `data.packet_id` in
the `claim-next` response. The error code stays `not_found` so
existing callers keep working; only the human-readable message
changes.

Justification: the wrong-kind prefixes are stable IDs produced by
`new_id("msg"|"lease"|...)` (see `go/pkg/mutations/claim.go`
issuance and the PG handler's id allocations); detecting them is a
cheap string prefix check that never has to query the DB.

### 2.3 Bug 2 - `release --requeue` for repo_write jobs

Refuse the call. Implementation lives in `HandleReleaseWork` at
`go/pkg/mutations/lifecycle.go:317-389`. Today line 363 reads
`if requeue && !isRepoWrite(job) { jobState = "queued";
messageState = "pending" }`. For a repo_write job with
`requeue=true` this falls through and silently parks the job in
`blocked`. Replace the silent fall-through with an explicit
`invalid_transition` (or matching) error before any write:

```go
if requeue && isRepoWrite(job) {
    return nil, rpc.NewError("invalid_transition",
        "release --requeue is not supported for repo_write jobs " +
        "(per D036 lazy-lease semantics); use `striatum recovery " +
        "requeue-stale` or `striatum recovery operator-publish`",
        nil)
}
```

Then keep the existing `jobState` / `messageState` derivation for
the non-repo_write branch. The CLI surfaces this as exit code != 0
(currently exit code 5 in the `invalid_transition` mapping --
verify the actual mapping in `src/striatum/cli/`); operators see a
single clear message instead of a silently dead run.

Justification:
- D036 (lazy-lease semantics for repo_write jobs) is the reason
  repo_write requeue is unsafe: the prior lane may have made
  uncommitted writes to the working tree, so blindly re-queuing the
  job to another lane risks a corrupted workspace. The "honor the
  requeue" path in SPEC option (1) is rejected because it would
  require new semantics around abandoning uncommitted writes -- out
  of scope.
- SPEC option (3) "add `release --abandon`" is also rejected for
  this workflow; we keep `release` semantics unchanged for the
  non-requeue path and only reject the unsupported combination. A
  separate verb can be considered later (see "Risks").

### 2.4 Skill-bundle worked example

Update the source-of-truth Jinja templates under
`src/striatum/plugins/templates/claude_code/skills/`
(`supervise.md.tmpl`, `claim-loop.md.tmpl`) to include a worked
example that:

1. Registers a session and starts a supervisor.
2. Calls `claim-next --json` and pulls `packet_id` from
   `data.packet_id` (the new top-level field) with `jq -r
   .data.packet_id` -- no nested-path spelunking.
3. Calls `supervise send --session-id $SESS --packet-id $PID` (or
   pastes from `data.next_steps.supervise_send`).
4. Notes that the supervised process reads the packet from stdin.

Regenerate the installed copies under `.claude/skills/` and
`.striatum/plugins/<profile>/skills/` with `striatum skills
install`. The `gemini` and `codex` profile templates may receive
the same example for parity.

## 5. Acceptance checklist

The verify job should cite each ID below. One numbered check per
bullet in SPEC "Acceptance / Definition of done."

- [DoD-1] `packet_id` is operator-discoverable from `claim-next`
  JSON without spelunking: `jq -r .data.packet_id` returns the
  active packet's ID, and `data.next_steps.supervise_send` carries
  the literal command line. The chosen path (top-level field +
  `next_steps`) is documented in both the `striatum-supervise` and
  `striatum-claim-loop` skill bundles.
- [DoD-2] `striatum supervise send --session-id <S> --packet-id
  msg_<...>` returns a non-zero exit with an error whose message
  names the wrong-kind ID and points at `data.packet_id` /
  `data.packet.packet_id` as the correct field. The same applies
  for `lease_*`, `job_*`, `sess_*`, and `sup_*` prefixes.
- [DoD-3] `striatum release --requeue --reason <r>
  --message-id <m> --lease-id <l>` on a repo_write job exits
  non-zero with `invalid_transition` (or the equivalent mapped
  exit code 5) and a message naming `recovery requeue-stale` /
  `recovery operator-publish` as the supported recovery verb. The
  job, message, and lease states are unchanged after the refused
  call (transactional: no partial release).
- [DoD-4] A worked end-to-end example in `striatum-supervise`
  and/or `striatum-claim-loop` goes from "fresh session" to
  "supervised agent reads a packet on stdin" using only the JSON
  paths from real CLI output -- specifically the new top-level
  `data.packet_id` and/or `data.next_steps.supervise_send`. No
  hand-written `python3 -c` JSON spelunking, no IDs the operator
  has to derive themselves.
- [DoD-5a] An integration-style test follows the worked example
  (or its scripted equivalent): `claim-next` -> parse top-level
  `packet_id` -> `supervise send` -> assert the packet bytes
  arrive on the supervisor's FIFO. This may be a Python-level test
  using the existing supervised-session harness.
- [DoD-5b] A test asserts `release --requeue` on a repo_write job
  either re-queues the job or refuses loudly; it must never leave
  the job silently in `blocked` with no claimable path.

```bash
SESS=$(striatum register-session --run-id <run> --role <r> \
  --lane codex --fresh --json | jq -r .data.session_id)
striatum supervise start --session-id $SESS
CN=$(striatum claim-next --session-id $SESS --json)
PID=$(printf '%s' "$CN" | jq -r .data.packet_id)
test -n "$PID"  # MUST NOT be empty
striatum supervise send --session-id $SESS --packet-id "$PID" --json
# wrong-kind probe (must fail with helpful message):
MID=$(printf '%s' "$CN" | jq -r .data.packet.lease.message_id)

  || echo "expected: wrong-kind error pointing at data.packet_id"
```

  || echo "expected: exit != 0, names recovery requeue-stale"

## 7. Risks and likely conflicts

### 7.1 Parallel issue workflows

- **GH #22** (daemon-migration owner) touches
  `src/striatum/cli/dispatch.py` and `src/striatum/daemon_pg/`
  (connection, client_admin, roles, migrations, config). The
  intersection with this workflow is **low**: #22 edits the doctor
  path and `daemon stop` semantics in `client_admin.py`; #24 edits
  the `claim_next` PG handler and the Python supervisor wrapper.
  The only shared file likely to merge-conflict is
  `src/striatum/cli/dispatch.py`, and only at the dispatch wiring
  (`daemon` vs `claim-next`/`release`/`supervise`) -- different
  blocks of the same `if args.command == ...` chain. Risk is
  minor; mechanical conflict resolution if it occurs.
- **GH #23** (Go daemon pidfile writer) touches
  `go/cmd/striatumd/main.go`, `go/pkg/striatumd/` (new), and only
  comment-level edits elsewhere. The Go-side intersection with
  this workflow is **lower** because #24 edits
  `go/pkg/mutations/lifecycle.go` and
  `go/pkg/mutations/supervision_control.go` (the `loadWorkPacket`
  helper), not the daemon process bootstrap. No file-level
  conflict is expected.

### 7.2 Recommended order

This workflow (#24) should run **after #22 and #23 have shipped**.
Rationale:

- #22 ships an operator-supported daemon-migration path; running
  #24's PG-harness tests against an un-migrated daemon is the same
  failure mode operators were hitting and is best avoided.
- #23 makes `daemon status` honest about a running daemon; the
  worked end-to-end example in the skill bundle implicitly assumes
  the daemon is reachable.
- Neither dependency is strictly blocking: #24 is contained to the
  RPC layer, the CLI formatter, and skill templates. If parallel
  shipping is preferred, the triager believes the only sharper
  carve-out is to defer the manual-verification claim-next ->
  supervise-send walk-through to a follow-up; the unit/integration
  tests do not depend on #22 or #23.

### 7.3 Implementation risks

- The wrong-kind prefix detector in `loadWorkPacket` must not
  introduce a TOCTOU between prefix-check and DB lookup. The fix
  is fully in-process; no risk.
- The new top-level `data.packet_id` field must not collide with
  an existing key. Confirmed: today `data` returned by claim_next
  is `{"status": "claimed", "packet": {...}, "supervisor_delivery":
  {...}?}`. Adding `packet_id` and `next_steps` is purely
  additive.
- The release-refusal change is observable behavior change.
  Existing operator runbooks or test fixtures that call
  `release --requeue` on a repo_write job and expect a `blocked`
  state will now see a non-zero exit. Audit fixtures under
  `tests/` and `examples/` and update any that depend on the silent
  fall-through. The triager believes this is exactly the
  surfacing-of-bug-as-error the SPEC requires; existing dependents
  are themselves buggy.
- The skill-bundle worked example must be kept in sync across the
  `claude_code`, `gemini`, and `codex` profile templates. The
  implementer should regenerate via `striatum skills install`
  rather than hand-editing generated files.
- D036 (lazy-lease semantics for repo_write) is referenced in the
  refusal message; the implementer should confirm D036 still
  describes the constraint accurately, and update the decision
  log entry if any wording changed under recent RFCs.
