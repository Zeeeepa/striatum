## Scope and posture

RFC 0038 V1 shipped the Vite + React + TypeScript scaffold and the four
island components, but the 3-way build review on dogfood-041 found that
the toolchain side never actually emitted real bundles — only
placeholders — and that the Jinja2/React prop contract drifted between
the two split implementers. RFC 0038 V1.5 closes those gaps without
adding new island surface.

Findings to land:

- **F1** — replace `placeholderIslandPlugin` with real Vite/Rollup output;
  commit real bundles to `src/striatum/web/static/build/`.
- **F2** — align the `/workflows/new` chooser catalog contract.
- **F3** — fix the `island-shared.js` double-mount risk in `vite.config.ts`.
- **F4** — keep `package_data` reachable when bundles move; remove the
  `__init__.py` shim only if package-data still resolves.
- **Supply-chain hygiene** — `package-lock.json` policy, `npm audit`
  baseline, dependency-tree review wired into Make / CI.

Non-goals: new island surface beyond F1–F4 wiring, hosted services, RFC
0038 future-work items. The legacy form-driven `workflow_edit.html`
fallback (`fallback?: boolean` on `WorkflowGraphEditorProps`,
`src/striatum/web/frontend/src/shared/types.ts:223`) stays untouched.

In `src/striatum/web/frontend/vite.config.ts`:

1. Delete lines 17–45 (the `placeholderIslandPlugin` factory).
2. Change `plugins: [placeholderIslandPlugin(), react()]`

### Bundle hash impact

Running `make ui-build` post-patch:

1. `vite build` emits real JS for every entry (~50–250 KB each, vs.

   shared chunks (React, react-dom, react-flow, shiki) and `style.css`.
2. `make ui-bundle-hash` regenerates `manifest.sha256` over every file
   in `src/striatum/web/static/build/` except `__init__.py` and
   `manifest.sha256` (per `Makefile:45-46`).
3. All six current `manifest.sha256` entries change.
4. CI `make ui-check-bundle` (`Makefile:48-49`) will `git diff
   --exit-code` and fail on uncommitted changes — meaning the first
   commit after this patch must include the regenerated bundles **and**
   the regenerated `manifest.sha256`.

## F2 — `/workflows/new` chooser prop contract mismatch

### Mismatch evidence

- Server returns `{"ok": true, "data": {"templates": [...]}}` from
  `_handle_workflow_templates` (`src/striatum/service.py:712`). Each
  entry is a catalog row with `template_id`, `kind`, `display_name`,
  `summary`, `recommended_for: list[str]`, `default_lane_sets: list[str]`.
- React expects `WorkflowTemplateCatalog = {shapes: [...], lane_sets:
  [...], modifiers?: [...]}` whose entries have `id`, `label`,
  `summary`, `recommended_for: string`, `default_lane_sets: string[]`
  (`src/striatum/web/frontend/src/shared/types.ts:93-129`).
- `WorkflowChooser` reads `catalog.shapes` / `catalog.lane_sets` /
  `catalog.modifiers` directly
  (`WorkflowChooser.tsx:132,138,146,284`), so the current contract
  drops the user on a "Failed to load workflow templates" error
  (`WorkflowChooser.tsx:229-237`) the moment real bundles ship —
  exactly the gemini critical reject from dogfood-041 intervention #6.
- The bundled catalog has no `modifiers` field at all
  (`src/striatum/workflow_templates/catalog.json` has only `shapes`,
  `lane_sets`, `harness_profile_fragments`); the React `modifiers` UI
  branch was speculative.

### Pick-which-side-moves

**The server side moves.** Justification (one sentence per RFC
guidance): a new `/v1/workflow-templates/catalog` JSON endpoint
returning the structured `{shapes, lane_sets}` shape is the smallest
diff that keeps the existing `/workflow-templates` flat-list contract
(consumed by the `striatum workflow templates list` CLI verb via the
`workflow` family in `service.py:407`) byte-stable, lets the frontend
keep its typed `WorkflowTemplateCatalog` contract untouched, and avoids
re-implementing field translation on every island that might consume
catalog shape in the future.

### Server change — concrete

Add to `src/striatum/service.py` (alongside `_handle_workflow_templates`
near line 707):

```python
def _handle_workflow_template_catalog(self) -> None:
    from striatum.workflow_generator import GeneratorError
    from striatum.workflow_generator.catalog import list_templates

    try:
        rows = list_templates()
        shapes = [_catalog_row_to_card(r) for r in rows if r["kind"] == "shape"]
        lane_sets = [_catalog_row_to_card(r) for r in rows if r["kind"] == "lane_set"]
        self._send_json(
            200,
            {"ok": True, "data": {"shapes": shapes, "lane_sets": lane_sets}},
        )
    except GeneratorError as exc:
        self._send_generator_error(exc)
```

…with a module-level helper next to the existing route handlers:

```python
def _catalog_row_to_card(row: JsonObject) -> JsonObject:
    return {
        "id": row["template_id"],
        "label": row["display_name"],
        "summary": row["summary"],
        "recommended_for": ", ".join(row.get("recommended_for") or []),
        "default_lane_sets": list(row.get("default_lane_sets") or []),
    }
```

Wire the route into the dispatcher in the same block that already
matches `/workflow-templates` and `/workflow-templates/...` near
`service.py:556-561`:

```python
if path == "/v1/workflow-templates/catalog":
    self._handle_workflow_template_catalog()
    return
```

Template prop update in `src/striatum/web/templates/workflow_new.html:12`:

```html
<div id="island-workflow-chooser" data-props='{{ {"allowMutations":
allow_mutations, "templatesUrl":
"/v1/workflow-templates/catalog", "previewUrl":
"/workflows/generate/preview", "generateUrl":
"/workflows/generate"} | tojson }}'></div>
```

Frontend dev-shell `data-props` in `index.html:46-48` updates to point
at `/v1/workflow-templates/catalog` too — dev shell parity matters so
`make ui-dev` exercises the same shape.

`WorkflowChooser.tsx` / `types.ts` / `api-client.ts` stay byte-stable.
The `modifiers?` field in `WorkflowTemplateCatalog` (`types.ts:96-101`)
stays optional and remains undefined until the catalog grows
modifiers — the existing `mods.length === 0` guard at
`WorkflowChooser.tsx:285-291` already handles this cleanly.

### Backward compatibility

- `GET /workflow-templates[?kind=…]` keeps its `{"templates": [...]}`

- `GET /workflow-templates/<id>` is unchanged.
- The new endpoint lives under `/v1/...` to match the existing JSON-API

## F3 — `island-shared.js` double-mount fix

### Root cause

`island-shared` is currently mapped to `src/main.ts` in
`vite.config.ts:10`. `src/main.ts:20-58` is a dev-shell that imports
each island component and calls `mount(...)` four times. `base.html:44`
loads `island-shared.js` on **every** page; pages that also load (say)
`island-workflow-chooser.js` then run `mount("island-workflow-chooser",
...)` twice — once from the shared bundle's `main.ts` side effects and
once from the chooser's `main.tsx` (`workflow-chooser/main.tsx:15-20`).
React's `createRoot()` does not noop a second time on the same DOM node
(it logs a warning and dual-renders), so this is a real correctness bug
once the placeholders are gone.

### Fix

Two coordinated edits:

1. **New file `src/striatum/web/frontend/src/shared/island-shared-entry.ts`**
   — the only side effect is to import `theme.css` so the shared
   stylesheet is part of the shared chunk graph; it does not import any
   island component or call `mount`:

   ```ts
   /**
    * Production entry for the `island-shared.js` bundle loaded by
    * `base.html` on every page. Keeps the shared chunk (React,
    * react-dom, helpers under `shared/`) reachable for per-island
    * bundles via Rollup's automatic code-splitting. MUST NOT call
    * `mount(...)` — per-island `main.tsx` files own mounting.
    */
   import "./theme.css";
   export {};
   ```

2. **`vite.config.ts:10`** — change the `island-shared` entry path to
   `resolve(srcDir, "shared/island-shared-entry.ts")` (the same line F1
   already touches).

3. **`src/main.ts`** keeps its current form for `make ui-dev`. To make
   the dev-only intent explicit and survive a future contributor's
   guess, the file is renamed
   `src/striatum/web/frontend/src/dev-shell.ts` and `index.html:76`
   updates its `<script>` to `src="/src/dev-shell.ts"`. Old name kept
   nowhere; tracked in CHANGELOG.

### How islands consume the shared chunk

After this fix, each island consumes the shared chunk through Rollup's
automatic code splitting (no source-level import of
`island-shared-entry.ts` required):

- `island-shared.js` is loaded by `base.html` first and pulls React,
  react-dom, and `mount.ts` into the browser cache.
- Per-island bundles (`island-workflow-chooser.js`, etc.) emit
  `import { createElement } from "react"` and `import { mount } from
  "../../shared/mount"` (already present, e.g.
  `workflow-chooser/main.tsx:9,11`). Vite/Rollup automatically routes
  those imports to the shared chunk; the per-island bundles do not
  re-bundle React.
- The double-mount path is gone because nothing in the shared bundle
  calls `mount` anymore.

### Verification

- Add a Vitest assertion that `island-shared-entry.ts` exports nothing
  but `{}` and that its module body has no `mount(` reference (regex
  check; pre-merge gate, not runtime — guards against the easy
  regression of someone re-adding mount calls to the shared entry).
- Smoke check via `make ui-dev`: load `/workflows/new` and confirm
  React DevTools shows exactly one `<WorkflowChooser>` root (currently
  with the placeholders it shows none; post-F1+F3 it should show one).
- Existing Vitest `workflow-chooser.test.ts` still passes —
  `WorkflowChooser` itself is unchanged.

### Backward compatibility

- `/static/build/island-shared.js` URL is unchanged — `base.html:44`
  doesn't move.
- File size shrinks (no React component bodies in the shared entry —
  but the auto-generated React/react-dom chunk arrives in the same
  bundle), so callers see the same shared cache after one navigation.
- `make ui-dev` continues to work via `index.html:76`'s updated

## F4 — Vite output semantics vs package-data layout

### Surface that ships bundle paths

- `pyproject.toml:47-49`:
  - `"striatum.web.static"` package-data globs include `"build/*.js"`,
    `"build/*.css"`, `"build/*.sha256"`.
  - `"striatum.web.static.build"` package-data globs include `"*.js"`,
    `"*.css"`, `"*.sha256"`.
- `src/striatum/web/static/build/__init__.py` — present so
  `striatum.web.static.build` is importable, which lets the second
  `package-data` entry resolve under setuptools without
  `MANIFEST.in`.
- There is **no** `MANIFEST.in` in the tree (`ls MANIFEST.in` reports
  the file does not exist).

### Risk

Vite emits chunk files via `chunkFileNames: "island-shared-[hash].js"`
(`vite.config.ts:58`) — hashed names that the current `package-data`
globs (`build/*.js` and `*.js`) **do** match, so the wheel-side path
is safe. The actual hazard is the inverse: the current setup ships
files that the **server route table does not enumerate**, and the
server has no manifest-driven loader. A page that wants the
hashed shared chunk has to know its name. Three options:

1. **Keep entries deterministic; accept the auto chunk URLs as opaque.**
   `entryFileNames: "[name].js"` already gives the five island
   bundles fixed names (`vite.config.ts:57`). Vite emits the
   auto-shared chunk (`island-shared-[hash].js`) only if shared
   surface exceeds the per-entry threshold. Each `<script>` only
   references `island-<name>.js` and the browser loads the hashed
   chunk on demand because the entry file's own `import` statements
   already point at the right hashed name. Templates never need to
   know the hash.

2. **Disable chunking for the shared bundle.** Risky: forces every
   per-island bundle to include React, blowing up bundle sizes by
   roughly 130 KB per island.

3. **Generate a server-side manifest mapping**. Adds runtime complexity
   for no gain over option 1.

**Pick option 1.** The Jinja2 templates only reference deterministic
entry names (`base.html:44`, `view_tree.html:14`,
`workflow_edit.html:35`, `workflow_new.html:16`, `view_file.html:26`);
the hashed chunk is loaded transitively by the browser. No template
code reads the Vite `manifest` file.

### `manifest.sha256` is the integrity manifest, not the asset manifest

Vite's `manifest: true` setting (`vite.config.ts:52`) emits a
`.vite/manifest.json` mapping entries to chunk file names. That file
is **not** consumed by the Python server. The separate
`manifest.sha256` file generated by `make ui-bundle-hash`
(`Makefile:45-46`) is purely a CI integrity check — `make
ui-check-bundle` rebuilds and `git diff --exit-code`s the build
directory, so any bundle/manifest drift fails CI.

### Concrete F4 patch

Three small changes are sufficient:

1. **`pyproject.toml:48`** — extend the `"striatum.web.static"`
   globs to include the Vite manifest if we keep emitting it:
   `"build/*.js", "build/*.css", "build/*.sha256", "build/.vite/*.json"`.
   Otherwise set `manifest: false` in `vite.config.ts:52` (the simpler
   path — nothing reads `.vite/manifest.json`). **Recommend the
   simpler path**: change `manifest: true` to `manifest: false` and
   leave the package-data globs alone; the integrity manifest is
   `manifest.sha256`.

2. **`pyproject.toml:49`** — keep
   `"striatum.web.static.build" = ["*.js", "*.css", "*.sha256"]` as a
   belt-and-suspenders entry. It is harmless and protects against
   a future setuptools change in how nested package-data resolves
   through parent globs.

3. **`src/striatum/web/static/build/__init__.py`** — keep the file.
   Its only role is making `striatum.web.static.build` a valid Python
   subpackage so the second package-data line resolves. `make
   ui-bundle-hash` already excludes it
   (`Makefile:46`, `if p.is_file() and p.name not in
   {"__init__.py","manifest.sha256"}`).

### Verification

- `make package-smoke` (`Makefile:75-76`) already wheels the project

- The wheel filename and import surface are unchanged.

## Supply-chain hygiene

### Lockfile policy

- `src/striatum/web/frontend/package-lock.json` is committed and stays
  committed. `make ui-install` calls `npm install`, which respects the
  lockfile by default. Document the policy in
  `docs/FRONTEND_DEVELOPMENT.md` (or `docs/SPEC.md` if the former
  doesn't exist yet — RFC 0038 §6 lists it as a deliverable but
  dogfood-041 may have shipped it under a different filename;
  confirm before adding):
  - Lockfile is the source of truth for dependency versions.
  - CI uses `npm ci` (not `npm install`) to enforce lockfile == registry.
  - Any change to `package.json` must regenerate `package-lock.json`
    in the same commit; CI fails otherwise.

## Open questions

- Is renaming `main.ts` → `dev-shell.ts` worth the churn vs. leaving
  it named and only changing what `island-shared` points at?
  **Recommendation: yes, rename.** The current filename implies a
  production role it no longer plays after F3, and a future
  contributor will re-wire it on autopilot if the name stays.
- Should `npm audit --omit=dev` be the comparison surface or
  `npm audit` (full)? **Recommendation: dev-omit.** Operators never
  install dev tooling (TypeScript, Vitest, jsdom); CI advisories on
  dev-only deps would create churn without operator risk.

  modifier surface? **Recommendation: no — V1.5 ships shapes +
  lane_sets only, matching the current catalog. The React
  `modifiers?` branch stays dormant (already guarded by

  later RFC adds catalog modifiers.
