## CLI surface

```
striatum init --with-ddd-layout [--json]

# Composable with --with-skills:
striatum init --with-skills claude_code --with-ddd-layout [--json]
```

The `--with-ddd-layout` flag is opt-in and defaults to off.
Plain `striatum init` produces output byte-identical to
v1.7.0.

## Envelope shape

```json
{
  "ok": true,
  "data": {
    "state_dir": "/path/to/repo/.striatum",
    "db": "/path/to/repo/.striatum/state.sqlite3",
    "ddd_layout": {
      "layout": "ddd",
      "files": [
        {"path": "docs/SPEC.md", "status": "created"},
        {"path": "docs/PRD.md", "status": "created"},
        {"path": "docs/DECISION_LOG.md", "status": "created"},
        {"path": "docs/UBIQUITOUS_LANGUAGE.md", "status": "created"},
        {"path": "docs/DDD.md", "status": "created"},
        {"path": "docs/rfcs/README.md", "status": "created"},
        {"path": "docs/rfcs/0001-template.md", "status": "created"}
      ],
      "dry_run": false
    }
  }
}
```

When run a second time (or against a partially-overlapping repo),
each existing file's entry switches to
`{"status": "skipped", "reason": "exists"}`.

## Composability with `--with-skills` (Finding 1 note)

Per the design review's Finding 1, the V1 design's intended
first-time-operator experience is to combine flags:

```
striatum init --with-skills claude_code --with-ddd-layout
```

This produces both envelopes nested under their own keys
(`data.skills` and `data.ddd_layout`). The two scaffolds are
orthogonal: skills are agent-facing config (`.claude/skills/`,
etc.); the DDD scaffold is human-facing documentation
(`docs/`).

## Out of scope (V1)

- `--force` and `--dry-run` flags (reserved in the API
  signature for V1.5).
- Template parameter substitution (`.md.tmpl` → V1.5 if
  operators ask).
- Multiple layouts (V1 ships `ddd` only).
- Doctor check for missing layout (V1.5+).
- `striatum scaffold sync` upgrade verb (deferred per RFC
  non-goals).
